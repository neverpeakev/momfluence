## Root cause
The IG container is created successfully (POST `/{ig-id}/media` returns a creation_id), but the very first GET `/{creation_id}?fields=status_code` 1.5s later returns 400 with subcode 33 — "this object does not exist, cannot be loaded due to missing permissions, or cannot support this operation." Meta appears to have tightened post-create visibility latency around 2026-05-23: the container isn't queryable at 1.5s but would settle within a few more seconds.

The existing polling loop threw on the first non-200 instead of treating it as a transient "not yet visible" condition, so we never gave Meta the chance to make the container readable.

## Fix
PR: claude/fix-content-cron-2026-05-26 — `app/api/social/ig-mirror/route.ts`
- Bump first-poll delay from 1.5s → 3s
- Extend polling loop from 8 → 10 iterations
- Treat non-200 status-check responses as transient (continue polling); only throw after all iterations exhausted, surfacing the last error
- Terminal container states (`ERROR`, `EXPIRED`) still throw immediately

After this lands, the next manual rerun on the failed rows for 05-23/05-24/05-26 will need their `status` reset from `ig_failed` to `fb_published` (and `error_message`/`errored_at` cleared) — the mirror cron skips `ig_failed` rows by design.
