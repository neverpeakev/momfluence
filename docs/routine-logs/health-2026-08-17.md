## Root cause
`app/api/social/ig-mirror/route.ts` had three early-return paths — missing env vars, `fetchPageContext` failure, `listPendingIgMirror` empty — that returned HTTP 200 with a `message` field in the JSON body and never touched the pending rows. When the Meta user token (`META_MARKETING_API_TOKEN` in Vercel `momfluence-platform`) expired around late May, every subsequent run hit the `auth/page-context` branch, logged nothing at error level, and left rows untouched.

Signals that pointed here:
- Vercel runtime logs show `GET /api/social/ig-mirror 200 [info/edge-middleware]` at 14:15:08 UTC, no serverless log line, no runtime-error cluster.
- `listPendingIgMirror` filters on `status = 'fb_published' AND fb_published_at IS NOT NULL AND ig_published_at IS NULL`. Today's row satisfies all three, so the "nothing to mirror" branch is out.
- The per-row failure branch calls `markFailed`, which would have written `error_message`. It didn't. So the failure is above the row loop, and the only pre-loop branch that returns 200 without touching state is `fetchPageContext`.
- FB posts still going out means the FB page publish path (which uses the same `META_MARKETING_API_TOKEN`) has a different code path or a different token. Worth verifying with the operator.

## Action required from you
1. Rotate `META_MARKETING_API_TOKEN` in Vercel (project `momfluence-platform`). Long-lived Facebook Page tokens can be invalidated by password changes, permission changes on the App, or the 60-day non-refresh window.
2. Merge PR (see below).
3. After deploy, trigger a manual drain: `curl -X POST -H "Authorization: Bearer $CRON_SECRET" https://momfluence.app/api/social/ig-mirror`. Instagram publishes are rate-limited to 25/24h per account, so 21 in one shot is fine but on the edge — watch for a rate-limit error on the last few and back off if needed.
4. If FB is still publishing on the same token, there may be two Meta tokens in the env — the FB generate path may use `META_PAGE_ACCESS_TOKEN` directly instead of doing the `/me/accounts` lookup. Worth reconciling so the outage on either side is easier to spot next time.

## Fix
Branch: `claude/fix-content-cron-2026-08-17`
PR: (see push output — created via github MCP)

`app/api/social/ig-mirror/route.ts`: whenever the endpoint bails out AFTER loading pending rows but BEFORE looping (missing env, expired token, IG-account-lookup failure), it now calls `markFailed(id, "ig", <reason>)` on each pending row and writes a `console.error`. Rows will surface as `ig_failed` with a real `error_message`, the health check will see them, and the next outage becomes a day-1 signal instead of a day-82 discovery.

Behavior trade-off: previously, a transient token outage left rows in `fb_published` and they'd be re-attempted daily. Now they move to `ig_failed` on the first outage and need a manual reset (SQL: `UPDATE generated_posts SET status='fb_published', errored_at=NULL, error_message=NULL WHERE status='ig_failed' AND ig_published_at IS NULL AND id IN (...)`). That matches the existing per-row-failure contract already documented in the file header ("Failed rows are marked ig_failed with the error message and will NOT be retried by future runs").
