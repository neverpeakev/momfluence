## Root cause
Two layers:

1. **Silent failure (code bug).** `app/api/social/ig-mirror/route.ts` calls `fetchPageContext()` before iterating pending rows. When that throws (e.g. the `instagram_business_account` lookup returns nothing, or `/me/accounts` rejects), the handler returns 200 with `message: "auth/page-context: ..."` in the JSON body but (a) does not `console.error` and (b) does not mark the pending rows `ig_failed`. The cron caller discards the body, so the failure is invisible in Vercel runtime logs (the path just shows `GET /api/social/ig-mirror 200`) and invisible in the database (rows stay at `fb_published` with `error_message=null`, so the next cron run re-fetches the same rows and fails the same way). This is why the May 23–26 batch had visible `ig_failed` rows (failure happened during per-row IG publishing, which has its own `markFailed` path) but everything after May 29 is invisible (failure moved upstream to `fetchPageContext`).

2. **Underlying Meta auth issue (infra).** The most likely upstream cause is loss of `instagram_basic` / `instagram_content_publish` scope on the Meta system-user token, or the FB Page ↔ IG Business Account link breaking in Meta Business Suite. The FB cron uses the same `/me/accounts` call minutes earlier and works, so the failure is at `GET /{pageId}?fields=instagram_business_account` — either an empty `instagram_business_account` field or a 4xx. Cannot confirm exact Meta-side error until the code-bug fix lands and a real error message surfaces (or until an operator inspects Meta Business Suite directly).

## Fix (PR)
Branch: `claude/fix-content-cron-2026-06-17`
- `app/api/social/ig-mirror/route.ts` — in the `fetchPageContext` catch, `console.error` the failure and call `markFailed(row.id, "ig", ...)` for every row in `pending` so the rows surface as `ig_failed` with a real `error_message`. The 200 response now reports `failed: pending.length` and a `details` array with each slug.

This is the *visibility* fix only. After it deploys and tomorrow's 14:15 cron runs, the row's `error_message` will reveal the Meta-side cause. At that point the operator can re-grant scopes / re-link the page in Meta Business Suite. (Not auto-fixable in code.)
