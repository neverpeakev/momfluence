## Most likely root cause
The 200-with-no-row-update pattern, combined with no `error_message` on any stuck row, narrows the failure to `fetchPageContext` in `app/api/social/ig-mirror/route.ts`. That path:
1. calls `/me/accounts` (page list via system user token) — known-working since FB cron uses the same call and succeeds daily, AND
2. calls `/{pageId}?fields=instagram_business_account` (page-token-scoped IG link lookup).

Step 2 is the prime suspect — either the page-scoped token is missing `instagram_basic` / `instagram_content_publish`, or the IG-FB link broke. Last known good 2026-05-27 → first known bad 2026-05-29 brackets a likely token / scope change. Could not confirm with direct invocation (no `CRON_SECRET` available in routine env) and Vercel runtime-logs query timed out for the 7-day window.

## Code bug (independent of root cause)
`fetchPageContext` failures return HTTP 200 with `ok: false` and DO NOT call `markFailed` on the pending rows. That is why this loop ran undetected for a month. Three Vercel-cron-visible signals (non-200 status, runtime error logs, per-row `ig_failed` markers) were all suppressed.

## Fix in this PR
PR: see branch `claude/fix-content-cron-2026-06-27`.

`app/api/social/ig-mirror/route.ts`:
1. Page-context failure now logs to `console.error`, marks each pending row as `ig_failed` with the underlying message, and returns HTTP 500.
2. Missing-env-var path returns HTTP 500 + `console.error`.
3. Per-row publish failures now `console.error` the underlying message (previously only marked in DB).
4. Final response returns HTTP 500 if any row failed (so Vercel cron dashboard surfaces it).

This does NOT fix the root cause (which requires a fresh page access token or restored IG link). It DOES guarantee tomorrow's run will surface a real error in Vercel runtime logs + the `error_message` column, so the operator can diagnose.
