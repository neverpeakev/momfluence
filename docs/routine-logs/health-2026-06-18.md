### Pattern shift on 2026-05-23
The 3 `ig_failed` rows (2026-05-23, -24, -26) all carry the same Meta error:

```
IG status check → 400: {"error":{"message":"Authorization Error","code":100,
"type":"GraphMethodException","error_subcode":33,"fbtrace_id":"..."}}
```

Subcode 33 ("Unsupported get request") on an IG container status check almost always means the access token is missing `instagram_basic` / `instagram_content_publish` scope, or the IG Business Account is no longer linked to the FB Page.

Then on 2026-05-28 and every day after, the failure mode shifted from per-row error to **silent early-return**: no row gets `markFailed`, no `error_message` is written, the function just returns 200 with `{ok: false, message: "auth/page-context: ..."}` in the body. The cron run history shows no error-level Vercel runtime logs because the route had zero `console.error` calls on the early-return paths.

### Root cause (likely)
`fetchPageContext` in `app/api/social/ig-mirror/route.ts:58-78` is throwing — most likely on the `GET /{pageId}?fields=instagram_business_account` call (the IG-specific call the FB cron does not make). Two leading hypotheses:

1. **Meta token regression**: `META_MARKETING_API_TOKEN` was rotated or auto-refreshed around 2026-05-23 without `instagram_basic` / `instagram_content_publish` scopes. The FB cron only needs `pages_show_list` + `pages_manage_posts`, which is why it kept working.
2. **IG account unlinked**: Instagram Business Account `17841442248205840` was disconnected from FB Page `1086292991223812`, so the `instagram_business_account` field comes back empty and the IG lookup throws "No Instagram Business Account linked".

Both require **operator action** (Meta Business Suite), not a code fix.

## Code fix shipped
PR: `claude/fix-content-cron-2026-06-18` → adds observability so this cannot fail silently again. Specifically, in `app/api/social/ig-mirror/route.ts`:

1. `console.error` on the env-missing early return.
2. On `fetchPageContext` failure: log to stderr **and** call `markFailed` for every pending row so the error surfaces in `generated_posts.error_message` (DB observability) as well as in the response body.

No semantic change to the happy path; no retry-loop changes.
