### Where the zeros come from
`app/api/optimizer/tick/route.ts:176` sets `visits = ins?.clicks ?? 0`, where `ins` is the
Meta insights row for the ad matched to each variant. Ruled out in this run:

- **Not an ad-matching bug.** 9 of 10 arms have a populated `meta_ad_id`, so
  `listAds()` → creative-prefix matching is working. (Only `move-over-influencers` / `c17`
  has a null ad id — a pre-existing single-variant gap, not the cause of the blackout.)
- **Not a scope mismatch.** `listAds()` (meta-client.ts:106) and `getAdInsights()`
  (meta-client.ts:127) both query the same `META_AD_SET_ID`, so the 45 ads and the
  insights query cover the same ad set.
- **Not a Meta auth/config failure.** `listAds()` returned 45 ads and both calls share one
  `Promise.all`, so the insights call succeeded too — it simply returned no rows for
  `last_7d`.

**Conclusion: the ad set has had no delivery for ~89 days.** The optimizer is doing exactly
the right thing (refusing to act on no data); the ads themselves are not running. This needs
a human to check the Meta campaign/ad set status and budget — it is a spend/account
question, not a code question, so no PR was opened.

## Secondary: an observability gap worth fixing later

`app/api/optimizer/tick/route.ts:145-149` catches a Meta pull failure, calls `logTickError`,
then **continues**, and the later `finishTick` (line 259) records `data_pull_ok: true` with a
null `error_message`. A Meta outage would therefore look identical to a healthy tick in
`optimizer_ticks`. That did not cause today's zeros, but it is why a blackout this long could
sit unnoticed in the ticks table. Not fixed here — out of scope for this routine, which only
opens PRs for a broken cron.
