## Root cause (two layers)

**Underlying (why it stopped working):** almost certainly the Meta long-lived Page Access Token backing `META_MARKETING_API_TOKEN` expired or was invalidated. `fetchPageContext` in `app/api/social/ig-mirror/route.ts` calls `/me/accounts` and `/{pageId}?fields=instagram_business_account`; a bad token throws there. Needs manual re-auth of the Meta app and rotation of the Vercel env var — not fixable in code.

**Why it went unseen for 7 days (the observability bug):** the `fetchPageContext` catch block returns HTTP 200 with `ok: false, message: "auth/page-context: …"` and *never touches any DB row*. Result:
- Vercel Cron sees 200 → run is "successful", no alert.
- The `generated_posts` row keeps `error_message: null` → any daily audit that only checks `error_message`/`errored_at` reports healthy.
- Nothing calls `console.error`, so the Vercel runtime-log tab is empty for the failure path.

The route was engineered to "return 200 on transient failures so cron doesn't retry", but the tradeoff was total observability loss.

## Fix (this PR)
PR: (see branch `claude/fix-content-cron-2026-08-16`)

`app/api/social/ig-mirror/route.ts`
1. `fetchPageContext` failure now: `console.error`s the full message, stamps `errored_at` + `error_message` on every currently-pending row (via new `noteTransientFailure` — leaves `status='fb_published'` so rows stay retry-eligible), and returns HTTP 500 so Vercel cron dashboard shows red.
2. Missing env vars now log + return 500 instead of a silent 200.
3. Per-row `publishToIg` failures now `console.error` before writing `ig_failed`.
4. Final response returns 500 whenever `failed > 0`.

`lib/social/db.ts`
- Adds `noteTransientFailure(ids, message)`: writes `errored_at` + `error_message` without changing `status`. Used specifically for auth/context failures where rows should stay retry-eligible.
